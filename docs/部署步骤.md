# 从 0 到 1 部署（本机 / macOS）

当前验证过的组合：基础设施跑 Docker，Spring 后端和前端跑本机。LangChain 后端本机 Python 3.9.6 太旧,只能跑容器,暂未启用。

## 1. 前置条件

| 软件 | 要求 | 检查命令 |
|---|---|---|
| Docker Desktop | 已启动 | `docker ps` |
| JDK | 17 | `java -version` |
| Maven | 3.6+ | `mvn -v` |
| Node.js | 18+ | `node -v` |
| 大模型 | OpenAI 兼容的 URL + Key | 见第 2 步 |

## 2. 填配置

只有一个文件要填：`spring-ai-rag/config/application.yml`（已 gitignore，不会进版本库）。

```yaml
spring:
  ai:
    openai:
      api-key: <你的 key>
      base-url: https://<网关地址>        # 不要带 /v1，Spring AI 自己会拼
      chat:
        options:
          model: deepseek-v4-flash        # 别用推理模型，见第 10 节
      embedding:
        options:
          model: text-embedding-v4

rag:
  llm-provider: openai
  embedding-provider: openai
  jwt-secret: <随便一段 32 字符以上的随机串>   # 不填每次重启都变，已发的 token 全失效
  admin-password: admin123456              # 不填会随机生成，且只在首次启动建号
```

| 配置项 | 说明 |
|---|---|
| `base-url` | 带 `/v1` 也能跑，启动时会自动去掉并记一行日志 |
| `jwt-secret` | 必须固定，否则每次重启都要重新登录 |
| `admin-password` | 必须固定。留空会随机生成并只打印一次在启动日志里，而账号只在首次启动创建 —— 日志一丢就再也登不进去，只能删库里 `users` 表重建 |

## 3. 起基础设施

```bash
cd docker
docker compose up -d          # etcd + MinIO + Milvus + Neo4j + Attu
docker compose ps             # 等到 milvus 和 neo4j 都是 healthy，首次约 1~2 分钟
```

## 4. 起 Spring 后端

```bash
cd spring-ai-rag
mvn clean package                                      # 首次约 1 分钟
java -jar target/spring-ai-rag-1.0.0-SNAPSHOT.jar      # 必须在 spring-ai-rag/ 目录下执行
```

必须在 `spring-ai-rag/` 目录下起，因为 Spring Boot 是从**当前工作目录**的 `./config/` 加载凭据的。

启动日志出现这三行才算正常：

```
LLM HTTP client: Jetty (read/idle 300s, connect 15s)
Default chat provider: openai
Started RagApplication in 3.7 seconds
```

## 5. 起前端

```bash
cd frontend
npm install        # 首次
npm run dev
```

## 7. 数据存在哪

全在本机，不碰任何外部存储。

| 内容 | 位置 |
|---|---|
| 用户 / 知识库 / 文档 / 会话 | `data/rag.db`（SQLite） |
| 上传的原始文件 | `spring-ai-rag/uploads/` |
| 向量 | Docker volume `docker_milvus_data` |
| 知识图谱 | Docker volume `docker_neo4j_data` |

唯一出本机的是：分块文本发去做 embedding、问题和检索到的原文发去做生成。**这些内容会出现在大模型网关的日志里**，放公司资料前先确认网关的日志留存策略。

## 8. 验证部署成功

| 步骤 | 操作 | 预期 |
|---|---|---|
| 1 | 打开 http://localhost:3000 用 admin 登录 | 进入主界面 |
| 2 | 新建知识库 | 后端日志出现 `Created collection 'kb_xxx' with dimension 1024` |
| 3 | 上传一个 txt | 状态 `processing` → `completed`，约 2 分钟（含实体抽取，每个分块一次大模型调用） |
| 4 | 提问 | 有流式回答，且引用了文档原文 |

第 3 步慢是正常的。文档录入会对每个分块调一次大模型做实体抽取，这是知识图谱的来源，也是录入耗时的主要部分。

## 10. 几个已知的坑

| 现象 | 原因 / 处理 |
|---|---|
| 启动报 `sun.misc.Launcher$AppClassLoader` / `UnsupportedClassVersionError` | 用到了 JDK 8。本机 `java -version` 默认是 1.8，JDK 17 在 `/opt/homebrew/opt/openjdk@17`。用 `/opt/homebrew/opt/openjdk@17/bin/java -jar ...`，或先 `export JAVA_HOME=/opt/homebrew/opt/openjdk@17` |
| 登录报 `Invalid username or password` | `admin-password` 没固定，账号是首次启动用随机密码建的。删 `data/rag.db` 里的 `users` 行后重启重建 |
| 请求 404 且路径像 `/v1/v1/...` | `base-url` 带了 `/v1`。现在会自动去掉，只在日志里记一行，不会再 404 |
| 大文档上传后一直卡在 `processing`，日志报 `batch size is invalid, it should not be larger than N` | 网关的 `text-embedding-v4` 一次只收十几条文本，项目默认一批 64 条。已在 `config/application.yml` 把 `embedding-batch-size` 降到 8。注意这个 N 是**浮动的**（同一请求先后报过 20 和 10，网关背后是多个后端），所以别贴着上限设 |
| 文档永远显示 `processing`，日志里已没有新报错 | 录入是后台线程做的，重启进程会把在跑的任务丢掉，但数据库里的状态不会回滚。在界面上删掉这条文档重新上传即可 |
| 知识图谱是空的 | 实体抽取只在**录入时**跑。修改配置后已录入的文档不会自动补图，要重新上传 |
| 回答正常但图谱空、路由总是走默认 RAG | 阻塞型大模型调用超时了。这些失败都被 catch 住静默降级，只在后端日志里能看到 `Entity extraction failed` / `Query analysis failed`。超时已设为 5 分钟，如果还出现就是网关真的不通 |
| 换了大模型网关连不上，报 TLS 握手失败 | 出站 HTTP 客户端固定用 Jetty（见 `LlmHttpClientConfig`）。换成 JDK 自带客户端会被某些网关按 TLS 指纹拒绝，不要改。用 Python 的 `urllib` 压这个网关也会被拒，测接口请用 `curl` |
| 提问后要等一两分钟才出第一个字 | chat 模型配成了**推理模型**（如 `deepseek-v4-pro`）。回答之前有两次非流式调用（查询分析、重排），非流式意味着网关要等整个 completion 生成完才返回，推理 token 全算进等待。实测同一个查询分析提示词：pro 32.2s／1501 个推理 token，flash 3.4s／124 个，而有效输出长度一样。端到端首字等待 92.6s → 10~16s。换 `deepseek-v4-flash` |
| 回答明显是对的，但末尾附了"我对这个回答的把握不太大" | `confidence` 是按重排分数算的，而 `rerank-threshold: 0` 会保留 0 分段落，把均分拉低。答案质量不受影响，只是这句提示会误报 |
