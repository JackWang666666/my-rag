## 1. 启动入口

`RagApplication.java:10-15` —— 就是标准的 `@SpringBootApplication` + `run()`,没有特殊逻辑。

但启动前有一个关键的"暗箱操作":`config/OpenAiEnvironmentPostProcessor.java`,实现 `EnvironmentPostProcessor`,`getOrder()` 固定排最后(`Ordered.LOWEST_PRECEDENCE`),所以它在 `application.yml` 读完之后才跑,能看到并改写最终配置。它解决两个问题:

1. **没填 OPENAI_API_KEY 会导致整个应用启动失败** —— Spring AI 的 OpenAI 自动配置有5个急切单例(chat/embedding/image/转写/合成),哪怕 `LLM_PROVIDER=ollama` 纯本地部署也会在容器刷新阶段因为"key为空"直接报错退出。这个类检测到空key就塞一个占位符 `missing-openai-api-key`(第63/97-100行),让bean能构造出来,但不会被真的拿去调用(靠 `ProviderBeans.openAiConfigured()` 识别占位符,见第5节)。
2. **base-url 带 `/v1` 会导致 404** —— `OpenAiApi` 自己会拼 `/v1/chat/completions`,如果你填的网关地址已经带 `/v1`,就变成 `/v1/v1/...`。这个类自动裁剪掉尾部的 `/v1`(`stripApiVersionSuffix()`,第125-136行)并打一行日志。覆盖的三个属性是 `spring.ai.openai.base-url`、`.chat.base-url`、`.embedding.base-url`。

**配置加载优先级**(写在 `config/application.yml` 文件头注释里):
- `src/main/resources/application.yml` —— 打包进jar的默认值,敏感项留空靠环境变量兜底(`${X:default}`)
- `config/application.yml` —— 工作目录下的外部文件,优先级更高,写真实密钥,**不进版本库**

## 3. 核心链路一:上传文档

入口 `controller/DocumentController.java:67-92` `upload()`

```
DocumentController.upload()
  → permissions.requireKbWrite()                    鉴权
  → 校验扩展名/大小
  → 存文件到 uploadDir
  → store.createDocument(status=processing)         先建一行记录,立即返回给前端
  → @Async 调 ingestService.ingestFile(...)          真正的处理是异步的
```

`service/IngestService.java:93-122` `ingestFile()`:

```
IngestService.ingestFile()
  → documentService.parseAndSplit()      Tika提取文本 + TextSplitter.split() 分块
  → persist(kbId, docId, texts, metas)   核心四步:
       ① embeddingService.embedBatch(texts)              按 EMBEDDING_BATCH_SIZE 分批转向量
       ② retrievalService.insert(kbId, vectorChunks)     写入 Milvus(collection名 kb_<32hex>)
       ③ store.insertChunks(...)                         同时写入 SQLite chunks 表(供全文检索,Milvus的like只支持前缀)
       ④ graphService.extractAndStore(...)               若 graph-max-chunks>0,抽取实体三元组写入 Neo4j
  → 成功 store.markDocumentCompleted() / 失败 markDocumentFailed()
  → finally 删除本地临时文件
```

前端靠轮询 `GET /api/documents/{docId}` 看 status 变化。

删文档时(`DocumentController.java:141-161`):先删Milvus向量 → 删本地文件 → 删SQLite记录(级联删chunks)。**注意:删文档不会清理Neo4j图谱节点**,只有删整个知识库才会清(`KnowledgeBaseController.delete()`)。

## 4. 核心链路二:聊天问答

入口 `controller/ChatController.java:53-91` `chat()`,用 `SseEmitter` 流式推事件给前端。

`service/ChatService.java:133-236` `streamChat()` 的九步(括号是对应SSE事件名):

```
1. ensureSession()                              取/建会话                      → session 事件
2. 取历史(最近6条) + 最多3个全局知识库
3. queryAnalyzerService.analyze(...)            单次LLM调用:路由决策(rag/graph/
                                                 hybrid/direct)+ 改写2-3个query +
                                                 抽取图谱实体关键词                → metadata 事件
   (route=direct 直接跳到第7步生成答案,置信度固定0.9)
4. retrieve():
     embeddingService.embed(问题)               问题转向量
     retrievalService.search(...)               Milvus多路检索:主query取10条+
                                                 改写query各取5条+全局KB各取3条
     去重后 rerankerService.rerank(...)          LLM打分0-10,跟向量分0.7/0.3混合重排
5. graphService.getGraphContext(...)            route含graph时查Neo4j补充上下文
6. calculateConfidence()                        综合召回数量/分数/路由置信度算一个总分
7. llmService.stream(messages)                  拼prompt+历史+问题,流式生成答案        → chunk 事件
8. 置信度<0.5 时追加"把握不大"提示语
9. store.appendMessage()                        写回SQLite messages表                  → sources/done 事件
```

**角色速记表**:
| 类 | 角色 |
|---|---|
| QueryAnalyzerService | 路由决策 + query改写 |
| EmbeddingService | 文本转向量(上传和提问都用它) |
| RetrievalService | 纯Milvus向量检索 |
| RerankerService | 对检索结果二次打分排序 |
| GraphService | Neo4j图谱上下文补充 |
| LlmService | 最终答案生成的统一入口(也被前面几个服务拿去做阻塞式LLM调用) |

## 5. 多厂商模型怎么切换的

这是整个项目最绕的一块,分两层看:

**启动时装配**(`LlmConfig.java` / `EmbeddingConfig.java`):
- 用 `ObjectProvider<OpenAiChatModel/OllamaChatModel>` 懒解析bean是否存在
- `ProviderBeans.openAiConfigured(environment)` 判断openai是不是"真的配了"(识别第1节说的占位符key),不是单纯bean存在就算可用
- 每个可用model包进 `DynamicChatModel`/`DynamicEmbeddingModel`——内部用 `AtomicReference` 持有真实实现,可以被整体替换掉
- `ChatModelRegistry`/`EmbeddingModelRegistry` 是 `Map<String providerName, Model>` + `defaultModel`。**为什么不直接注入 `Map<String, ChatModel>`**:Spring会按bean name(`openAiChatModel`/`ollamaChatModel`)而非`openai`/`ollama`这种业务名去填充map,这是之前"切换无效"bug的根因,所以才自己包一层Registry。

**运行时请求**:
- `LlmService`/`EmbeddingService` 每次调用都从 `SettingsStore.current().getLlmProvider()/getEmbeddingProvider()` 实时读当前provider名,再 `registry.resolve(provider)` 取model——provider是**每次请求读的**,不是启动时写死的。

**运行时修改(管理员在设置页改配置)**:
```
SettingsController PUT
  → SettingsStore.update()
  → OpenAiClientFactory/OllamaClientFactory.buildXxx()   用新的base-url/model/key建一个新实例
  → registry.replace(provider, 新实例)                   换掉 DynamicXxxModel 内部的delegate
```
这就是"改设置不用重启"的完整链路。但如果一个provider启动时**根本没被offer过**(比如openai当时完全没配key),`replace()`是no-op,这种"从0到有"必须重启。

## 6. 鉴权与安全

过滤器链(`SecurityConfig.java:36-49`):CORS → CSRF关闭 → STATELESS → **JwtAuthFilter插在UsernamePasswordAuthenticationFilter之前** → `/api/auth/**`和`/health`放行,其余 `anyRequest().authenticated()`。

- `JwtAuthFilter` 从 `Authorization: Bearer` 头取token,一次性解析塞进SecurityContext(authorities=`ROLE_<ROLE>`)
- `JwtUtil` HS256签名,密钥来自 `rag.jwt-secret`,**必须跟Python后端的JWT_SECRET一致**才能token互通,密钥不足32字节直接拒绝启动
- `UserService` 用BCrypt(兼容Python端`$2b$`前缀),`@PostConstruct` 首次启动建管理员账号
- `PermissionService` 是集中授权规则:全局KB任何人可读/仅admin可写;私有KB仅owner/admin;非owner访问session返回404而不是403(避免暴露session是否存在)
- `CurrentUser.get()` 从SecurityContext读username+role,未认证抛 `ApiException(401)`

## 7. 配置项速查(`RagProperties.java`,前缀 `rag.*`)

| 配置项 | 要注意的点 |
|---|---|
| `db-path` | 必须跟Python后端的DB_PATH指向同一个文件 |
| `jwt-secret` | 留空=每次重启随机生成,之前token全失效 |
| `admin-password` | 留空=随机生成,打印在启动日志里,日志丢了只能删users表重建 |
| `cors-origins` | 禁止写 `*`(跟凭证请求冲突) |
| `embedding-batch-size` | 网关有后端上限限制时要调小,不是越大越好 |
| `graph-max-chunks` | 0=跳过知识图谱抽取(省时间) |
| `reranker-provider` | `local`是Python独有,Java端配了会自动降级成`llm` |

`SettingsStore.java` 的"运行时可改设置"机制:
- **立即生效**:llmProvider、embeddingProvider、rerankerProvider、chunkSize、chunkOverlap,以及openai/ollama的base-url/model/key(见第5节)
- **记录但要重启才生效**:Milvus host/port、Neo4j uri(这些client在启动时就建好了)

## 8. 数据存储

`store/Db.java` 里硬编码了SQLite的schema(`SCHEMA`常量),**跟Python后端的db.py必须字节级一致**。打开连接时设 `PRAGMA journal_mode=WAL` 等,支持两个后端并发访问同一个文件。表:

- `users`、`knowledge_bases`、`documents`、`chunks`(全文检索用)、`sessions`、`messages`、`feedback`

`store/MetadataStore.java` 是对每张表的CRUD封装(record类型),是Python端`store.py`的Java镜像。

`service/GraphService.java` 对应的图结构是固定的:`(:Entity {name, kb_id})-[:RELATION {type, kb_id}]->(:Entity)`,所有操作都带 `kb_id` 过滤实现知识库隔离。

## 9. 统一异常处理

`web/ApiException.java` + `web/ApiExceptionHandler.java`(`@RestControllerAdvice`):
- `ApiException` → 用自带状态码返回 `{detail, error}` 双key(兼容FastAPI格式)
- `IllegalArgumentException` → **故意**映射成500而不是400(这是库代码内部故障,不是客户端输入问题)
- 其余异常类型不处理,交给Spring Boot默认处理,避免把框架级404/安全拒绝也拍扁成500
